# Арена переговоров — сопроводительная документация

Интерактивный симулятор развития навыков переговоров. Разработан в рамках хакатона по ТЗ
«Симулятор развития навыков переговоров "Арена переговоров"» (Алабуга, 2026).

## 1. Аудитория, проблема, границы MVP

**Для кого.** Три пересекающиеся аудитории: (1) сотрудники, которым переговоры нужны по работе —
менеджеры по продажам, закупщики, HR, руководители; (2) корпоративное обучение / EdTech-платформы,
которым нужен инструмент для многократной безопасной практики без живого тренера на каждую сессию;
(3) сами обучающиеся, которым нужна честная, воспроизводимая обратная связь по своим формулировкам,
а не общий чек-лист.

**Проблема.** Очные тренинги и ролевые игры дают мало попыток, дорого масштабируются и редко
разбирают именно формулировки конкретного человека. Чтение теории (BATNA, SPIN, Гарвардский метод)
без практики не переносится в реальный диалог.

**Ценность решения.** Симулятор даёт неограниченное число попыток с реальным виртуальным
собеседником, где **исход зависит не от заранее прописанного сюжета, а от того, что именно написал
игрок** — детерминированный движок (см. §3) оценивает содержание и уместность каждой реплики и
считает по ним прогресс, а не просто "прокликивает" готовый сценарий.

**Что уже реализовано (MVP):**
- полный путь пользователя: выбор сценария → брифинг с контекстом → диалог с виртуальным оппонентом
  (иллюстрированный аватар с реакцией на настроение) → детальный разбор итогов;
- 2 многоуровневых сценария "из коробки" (продажа B2B-решения через привратника к ЛПР;
  удержание недовольного клиента) — оба с несколькими уровнями и подэтапами каждый;
- админ-панель с ручным редактором сценариев **и** генерацией сценария по контексту одним
  запросом (сфера, сложность, роль/тон/цели оппонента → LLM пишет содержание, движок сам считает
  баланс — см. §4);
- детерминированный игровой движок, полностью отделённый от LLM (§3);
- полный офлайн-режим (`MOCK_LLM=true`) — демо не ломается без интернета/ключа API;
- 137 автоматических тестов (юнит + интеграционные) движка, API и LLM-клиента.

**Что осознанно не реализовано / известные ограничения:**
- сценарии структурно линейны (Stage → Stage → Level → Level с воротами
  continue/advance/fail), а не ветвящееся дерево с несколькими явными путями. Вариативность финала
  (deal / partial / failed) и ранний обрыв при провале — есть; развилки с разным *содержанием*
  следующего шага в зависимости от выбора — нет;
- голос/видео-ввод не реализован (только текст) — по ТЗ это и не обязательно;
- аватар оппонента — иллюстративный (сгенерированные пользователем фото + Ken Burns-анимация
  видео, отрендеренная офлайн через Remotion), не «живой» ИИ-видеоаватар в реальном времени —
  осознанный выбор, чтобы не зависеть от платного API без запасного режима (см. ТЗ, «чего избегать»).

## 2. Путь пользователя

1. **`/`** — список опубликованных сценариев (карточки: домен, сложность, критерий успеха).
2. **`/scenario/[id]`** — брифинг: роль игрока, ситуация, с кем предстоит разговор (карточка
   оппонента), цель первого уровня, критерий успеха.
3. **`/play/[sessionId]`** — сам диалог: текстовый ввод реплики, ответ оппонента с озвученной
   через аватар реакцией (нейтрально/заинтересован/насторожен, слушает/говорит), прогресс-бар
   раунда и уровня.
4. **Итоги** (тот же экран после завершения): исход (deal/partial/failed), общий счёт, что
   получилось хорошо / что ухудшило результат, ключевой переломный момент диалога с объяснением,
   пример более сильной формулировки, разбор по этапам и по уровням.

Админ-контур: **`/admin`** — список сценариев, форма генерации по контексту, ручной редактор
(сценарий → уровни → подэтапы) с публикацией/снятием с публикации.

## 3. Архитектура и логика симуляции

### 3.1. Модель данных

```
Scenario (домен, сложность, роль игрока, ситуация, критерий успеха)
  └─ Level[] (order, роль/тон/цели оппонента на этом уровне, maxRounds, пороги)
       └─ Stage[] (order, type: CONTACT | DISCOVERY | PITCH | OBJECTION | CLOSING)

Session (снапшот NegotiationState целиком в JSON)
  └─ Turn[] (реплика, actionType, quality — для разбора итогов)
  └─ Feedback (текстовый разбор + все посчитанные цифры)
```

### 3.2. Разделение Engine / LLM — ключевое архитектурное решение

Это прямой ответ на риск, о котором явно предупреждает ТЗ («зависимости от платных API без
запасного режима»), и одновременно — решение для объяснимости и предсказуемости оценки.

**LLM отвечает только за:**
1. `classifyAction` — классифицировать последнюю реплику игрока в один из типов действия
   (`QUESTION`, `ARGUMENT`, `CONCESSION`, `PRESSURE`, `RAPPORT`, `CLARIFICATION`, `NEUTRAL`, `ABUSE`,
   `GIBBERISH`, `OFF_TOPIC`) и оценить её качество (0–100). **Не решает исход.**
2. `generateOpponentReply` — сгенерировать естественный текст реплики NPC в рамках уже посчитанного
   состояния. **Не решает переходы.**
3. `generateFeedback` — облечь в текст уже посчитанные движком факты (какой этап был сильнее,
   какая реплика стала переломной). **Не может подменить сами цифры** — числовые поля физически не
   читаются из ответа LLM на уровне кода (см. `toFeedbackResult` в `lib/llm/client.ts`).

**Engine (`lib/engine/`, без единого обращения к сети) решает всё остальное детерминированно:**
- на сколько сдвигается прогресс текущего подэтапа и доверие/интерес оппонента —
  по таблице `type действия × уместность для текущего Stage × quality` (`lib/engine/rules.ts`);
- когда подэтап/уровень пройден, когда сорван (`lib/engine/transition.ts`) — по порогам, заданным
  в `Level` (`advanceThreshold`, `failThreshold`, `maxRounds`);
- итоговый счёт и разбивку по этапам для экрана итогов (`lib/engine/score.ts`, `feedbackFacts.ts`).

У каждой LLM-функции есть детерминированный fallback (по сети/парсингу/`MOCK_LLM=true`), и он не
«урезанная заглушка», а содержательная логика на тех же посчитанных фактах — движок и игровой цикл
работают одинаково в обоих режимах, меняется только качество текста.

Отдельно — оскорбления/мат детектируются **детерминированным regex-предохранителем** ещё до
обращения к LLM (см. `ABUSE_PATTERN` в `lib/llm/client.ts`): токсичный тон не должен то ловиться,
то нет, в зависимости от настроения модели в конкретном вызове.

### 3.3. Настроение оппонента и аватар

`opponent.trust` (0–100, внутренняя метрика Engine) огрубляется в презентационную категорию
(`positive` / `neutral` / `negative`, см. `lib/engine/mood.ts`) — она и определяет, какое фото
оппонента показывать и какого цвета кольцо вокруг аватара. Во время отправки реплики аватар
переходит в состояние "слушает" (пульсирующее кольцо), после ответа — в "говорит" (ускоренное
воспроизведение видео + анимация звуковой волны).

## 4. Конфигурируемость под контекст (ТЗ п.2)

Администратор в `/admin` задаёт: **сферу/тему переговоров, сложность (EASY/MEDIUM/HARD), роль,
тон и цели оппонента**. По кнопке «Сгенерировать» это уходит в
`POST /api/scenarios/generate` → `generateScenarioDraft` (LLM пишет название, роль игрока,
ситуацию, критерий успеха и содержимое 2 уровней с подэтапами) → создаётся **неопубликованный**
черновик сценария, который администратор проверяет и правит в обычном редакторе перед публикацией.

Числовой баланс уровня (`maxRounds`, `advanceThreshold`, `failThreshold`) считает **не LLM, а сам
эндпоинт** — по количеству подэтапов, детерминированной формулой, откалиброванной по живым
прогонам на реальной (не mock) модели в этом же проекте. Так LLM не может создать заведомо
непроходимый или наоборот тривиальный уровень числами — она отвечает только за контент.

При `MOCK_LLM=true` или сбое сети та же кнопка создаёт валидный играбельный черновик офлайн, по
простому шаблону на основе тех же 5 введённых параметров.

## 5. Технологии, библиотеки, внешние сервисы

- **Next.js 16 (App Router, Turbopack) + React 19 + TypeScript** — фронтенд и API-роуты в одном
  проекте.
- **Prisma 6 + PostgreSQL** — хранение сценариев/сессий; демо не «ломается» после перезапуска.
- **Tailwind CSS v4** — вся анимация (появление карточек, дыхание/кольца аватара) — чистый CSS,
  без сторонних анимационных библиотек.
- **Vitest** — 137 тестов (движок, LLM-клиент с моками, API-роуты).
- **Groq API** (`GROQ_API_KEY`, опционально) — LLM-вызовы (`classifyAction`, `generateOpponentReply`,
  `generateFeedback`, `generateScenarioDraft`), модель по умолчанию `openai/gpt-oss-120b`
  (настраивается через `LLM_MODEL`). Ключ получается на [console.groq.com](https://console.groq.com).
  **Не обязателен** — `MOCK_LLM="true"` полностью отключает сетевые вызовы.
- **Remotion** (`avatar-video/`, отдельный под-проект вне основного приложения) — офлайн-рендер
  Ken Burns-видео аватара оппонента из фото, сгенерированных пользователем; результат
  (`public/avatar/*.mp4`) уже лежит в репозитории, для запуска приложения Remotion не нужен.

Все переменные окружения и их назначение — в [`.env.example`](./.env.example).

## 6. Сборка, запуск и демонстрация

Полная инструкция локального запуска — в [`README.md`](./README.md#быстрый-старт-локальный-запуск).

**Путь для демонстрации жюри** (после `npm run dev`):
1. `/` — выбрать любой из двух опубликованных сценариев.
2. `/scenario/[id]` — посмотреть брифинг, нажать «Начать переговоры».
3. `/play/[sessionId]` — провести несколько реплик; для наглядности стоит явно менять стратегию
   между репликами (тёплое приветствие → уточняющие вопросы → аргумент/уступка), чтобы было видно,
   как меняется настроение оппонента (аватар) и почему.
4. Довести уровень до провала или до конца раундов — откроется экран итогов с полным разбором.
5. `/admin` — показать генерацию нового сценария по контексту (5 полей → готовый черновик) и
   ручной редактор для его донастройки.

Быстрая проверка тестами: `npm run test` (137 тестов, движок покрыт отдельно от UI).
