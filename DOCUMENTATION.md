## 1. Целевая аудитория, проблема, границы MVP

**Для кого.** Три пересекающиеся аудитории:

1. **Сотрудники**, которым переговоры нужны по работе — менеджеры по продажам, закупщики, HR,
   руководители.
2. **Корпоративное обучение / EdTech-платформы** — нужен инструмент многократной безопасной
   практики без живого тренера на каждую сессию.
3. **Сами обучающиеся** — нужна честная, воспроизводимая обратная связь по своим формулировкам, а
   не общий чек-лист "было хорошо / было плохо".

**Проблема.** Очные тренинги и ролевые игры дают мало попыток, дорого масштабируются и редко
разбирают формулировки конкретного человека. Чтение теории (BATNA, SPIN, Гарвардский метод) без
практики не переносится в реальный диалог: человек помнит принципы, но не успевает довести их до
автоматизма в живом разговоре.

**Ценность решения.** Симулятор даёт неограниченное число попыток с виртуальным собеседником, где
**исход зависит не от заранее прописанного сюжета, а от того, что именно написал игрок**:
детерминированный движок (раздел 4) классифицирует и оценивает уместность каждой реплики и по этим
данным считает прогресс, доверие оппонента и итоговый счёт, а сюжет при этом ещё и физически
**разветвляется** в зависимости от выбранной стратегии (раздел 5) — а не просто "прокликивается" по
фиксированному сценарию с косметически разным текстом.

### Что реализовано (MVP)

- Полный путь пользователя: выбор сценария → брифинг с контекстом → диалог с виртуальным
  оппонентом (иллюстрированный аватар, реагирующий на настроение) → детальный разбор итогов.
- 2 многоуровневых сценария "из коробки", **оба с реальным ветвлением** (не просто разными
  финалами, а разным содержанием следующего этапа в зависимости от стратегии игрока — см. раздел 5):
  продажа B2B-решения через привратника к директору; удержание недовольного клиента.
- Админ-панель с ручным редактором сценариев **и** генерацией сценария по контексту одним запросом
  (сфера, сложность, роль/тон/цели оппонента → LLM пишет содержание, движок сам считает баланс —
  раздел 6).
- Детерминированный игровой движок, полностью отделённый от LLM (раздел 4).
- Полный офлайн-режим (`MOCK_LLM=true`) — демо не ломается без интернета/ключа API.
- CI на GitHub Actions: типы, линтер, тесты и прод-сборка проверяются на каждый пуш и PR (раздел 8).
- Автоматические тесты движка, API и LLM-клиента (раздел 8).

### Что осознанно не реализовано / известные ограничения

Подробный список и обоснование каждого пункта — раздел 10. Коротко: голос/видео-ввод (не
обязателен по ТЗ, приоритет отдан тексту), аватар оппонента иллюстративный, а не «живой»
ИИ-видеоаватар в реальном времени, генерация сценария создаёт линейный черновик (ветвление в
сгенерированных сценариях администратор добавляет вручную в редакторе — см. раздел 5).

## 2. Путь пользователя

1. **`/`** — список опубликованных сценариев (карточки: домен, сложность, критерий успеха,
   количество уровней).
2. **`/scenario/[id]`** — брифинг: роль игрока, ситуация, с кем предстоит разговор (карточка
   оппонента), цель первого уровня, критерий успеха всего сценария.
3. **`/play/[sessionId]`** — сам диалог: текстовый ввод реплики, ответ оппонента с реакцией через
   аватар (нейтрально / заинтересован / насторожен, "слушает" / "говорит"), прогресс-бар раунда и
   уровня.
4. **Итоги** (тот же экран после завершения): исход (deal / partial / failed), общий счёт, что
   получилось хорошо / что ухудшило результат, ключевой переломный момент диалога с объяснением,
   пример более сильной формулировки, разбор по этапам, разбор по уровням (включая то, какая
   ветка развилки была пройдена на каждом уровне, если она там есть).

Админ-контур: **`/admin`** — список сценариев, форма генерации по контексту, ручной редактор
(сценарий → уровни → подэтапы, включая варианты развилки) с публикацией/снятием с публикации.

## 3. Архитектура и модель данных

### 3.1. Стек

Next.js (App Router) на фронтенде и бэкенде в одном проекте, PostgreSQL через Prisma ORM. Подробнее
— раздел 7.

### 3.2. Модель данных

```
Scenario (домен, сложность, роль игрока, ситуация, критерий успеха, isPublished)
  └─ Level[] (order, роль/тон/цели оппонента на этом уровне, maxRounds, advanceThreshold, failThreshold)
       └─ Stage[] (order, type: CONTACT|DISCOVERY|PITCH|OBJECTION|CLOSING, branchKey: null|"soft"|"hard")

Session (снапшот NegotiationState целиком в JSON — единственный источник истины об игровом прогрессе)
  └─ Turn[] (текст реплики, actionType, actionQuality, stageType — для разбора итогов)
  └─ Feedback (текстовый разбор + все посчитанные цифры, ровно одна запись на сессию)
```

Ключевое решение, определяющее весь остальной дизайн: **`Session.state` хранит НЕ ссылки на
"текущий Stage", а полный расчётный снапшот** (`NegotiationState`, см. `lib/engine/types.ts`) —
округа доверия/интереса оппонента, накопленные метрики игрока, прогресс текущего этапа,
вероятность соглашения, история уровней. Это значит, что вся игровая логика воспроизводима и
тестируема как чистая функция `(state, action) -> state'`, без обращения к БД внутри самого расчёта
(она нужна только чтобы прочитать снапшот до и записать после).

`Stage.branchKey` — единственное поле, отвечающее за ветвление: несколько `Stage` могут делить один
`order` внутри `Level`, и это **и есть** развилка (раздел 5).

`Turn.stageType` записывается напрямую из уже посчитанного состояния движка в момент создания
хода, а не резолвится задним числом по `(levelOrder, stageOrder)` — при ветвлении несколько `Stage`
могут делить один `order`, и резолв "какой именно из них" по одному `order` стал бы неоднозначным
после того, как разговор уже прошёл дальше.

### 3.3. Разделение Engine / LLM — ключевое архитектурное решение

Прямой ответ на риск, о котором явно предупреждает ТЗ («зависимости от платных API без запасного
режима»), и одновременно решение для объяснимости и предсказуемости оценки.

**LLM (`lib/llm/`, Groq API) отвечает только за:**

1. `classifyAction` — классифицировать последнюю реплику игрока в один из типов действия
   (`QUESTION`, `ARGUMENT`, `CONCESSION`, `PRESSURE`, `RAPPORT`, `CLARIFICATION`, `NEUTRAL`, `ABUSE`,
   `GIBBERISH`, `OFF_TOPIC`) и оценить её качество (0–100). **Не решает исход и не решает переходы.**
2. `generateOpponentReply` — сгенерировать естественный текст реплики NPC в рамках уже посчитанного
   состояния (включая то, какая ветка развилки уже выбрана движком).
3. `generateFeedback` — облечь в текст уже посчитанные движком факты (какой этап был сильнее, какая
   реплика стала переломной, какая ветка была пройдена). **Не может подменить сами цифры** —
   числовые поля физически не читаются из ответа LLM на уровне кода (`toFeedbackResult` в
   `lib/llm/client.ts` — только строки; сравните со схемой `FeedbackResult`, где нет ни одного
   `number`).
4. `generateScenarioDraft` — по 5 параметрам администратора написать содержание черновика сценария
   (раздел 6). Баланс уровня (числа) считает не она.

**Engine (`lib/engine/`, без единого обращения к сети) решает всё остальное детерминированно:**

- на сколько сдвигается прогресс текущего подэтапа и доверие/интерес оппонента — по таблице
  `type действия × уместность для текущего Stage × quality` (`lib/engine/rules.ts`);
- когда подэтап/уровень пройден, когда сорван, **в какую сторону идёт развилка**
  (`lib/engine/transition.ts`, раздел 5) — по порогам и накопленным метрикам, заданным в состоянии;
- итоговый счёт и разбивку по этапам для экрана итогов (`lib/engine/score.ts`, `feedbackFacts.ts`).

У каждой LLM-функции есть детерминированный fallback (по сети/парсингу/`MOCK_LLM=true`), и это не
«урезанная заглушка», а содержательная логика на тех же посчитанных фактах — движок и игровой цикл
работают одинаково в обоих режимах, меняется только качество текста.

Отдельно — оскорбления/мат детектируются **детерминированным regex-предохранителем** ещё до
обращения к LLM (`ABUSE_PATTERN` в `lib/llm/client.ts`, с границами по кириллическим буквам, чтобы
не ловить ложные срабатывания на подстроках вроде «...бля» внутри «рублях»): токсичный тон не
должен то ловиться, то нет, в зависимости от настроения модели в конкретном вызове.

### 3.4. Настроение оппонента и аватар

`opponent.trust` (0–100, внутренняя метрика движка) огрубляется в презентационную категорию
(`positive` / `neutral` / `negative`, `lib/engine/mood.ts`) — она определяет, какое фото оппонента
показывать и какого цвета кольцо вокруг аватара. Во время отправки реплики аватар переходит в
состояние "слушает" (пульсирующее кольцо), после ответа — в "говорит" (ускоренное воспроизведение
видео + анимация звуковой волны).

## 4. Логика симуляции: детерминированный движок

Полный цикл одного хода (`app/api/sessions/[id]/turn/route.ts`, обёрнут в одну транзакцию с
`pg_advisory_xact_lock` по id сессии — сериализует конкурентные запросы к одной и той же сессии,
например двойной клик "Отправить"):

1. `classifyAction` (LLM) — только классификация, без решений.
2. `applyAction` (движок, `lib/engine/apply.ts`) — чистая функция: по таблице `getBaseActionEffect`
   и `getStageProgressDelta` (`lib/engine/rules.ts`) считает новые `player`, `opponent`,
   `stageProgress`, `negotiation.agreementProbability`, а также копит `branchSignal` для развилки
   (раздел 5).
3. `evaluateTransition` (движок, `lib/engine/transition.ts`) — по новому состоянию решает один из
   пяти исходов: `continue` / `advance-stage` / `advance-level` / `fail-level` / `finish`. Именно
   здесь, при переходе на Stage-развилку, один раз решается и фиксируется, в какую сторону идёт
   сюжет.
4. В зависимости от перехода: LLM-реплика оппонента (`continue`/`advance-stage`), заранее заданная
   `openingLine` нового уровня (`advance-level`, без LLM) или детерминированная закрывающая фраза
   (`fail-level`/`finish`).
5. Если сессия завершилась — `lib/engine/feedbackFacts.ts` считает факты (разбивка по этапам,
   ключевой момент) из уже сохранённых `Turn`, и только это, в текстовом виде, дополняет LLM
   (`generateFeedback`).

### 4.1. Таблица правил действия × уместность

`lib/engine/rules.ts` — две плоские таблицы, каждую ячейку можно прочитать и протестировать
отдельно:

- `getBaseActionEffect(actionType, quality)` — базовый эффект действия (не зависящий от текущего
  Stage): `delta = quality - 50` определяет знак и силу воздействия на `player`/`opponent`/
  `agreementProbability`. Например, `CONCESSION` при высоком качестве заметно поднимает
  `agreementProbability` и `opponent.trust`; `PRESSURE` при низком качестве роняет `trust` и
  поднимает `resistance`; `ABUSE` даёт фиксированный штраф `-15` к `trust`, не зависящий от
  качества (оскорбление не бывает "качественным").
- `STAGE_ACTION_RELEVANCE[stageType][actionType]` — насколько тип действия уместен именно на этом
  этапе (от `2`, ключевое действие, до `-2`, контрпродуктивно). Например, `RAPPORT` — ключевое
  действие для `CONTACT`, но контрпродуктивно там же `CONCESSION`/`PRESSURE`; на `CLOSING`,
  наоборот, ключевое действие — `CONCESSION`, а `PRESSURE` там же карается сильнее всего (`-2`).
  Именно это произведение (`getStageProgressDelta`) двигает прогресс текущего подэтапа — то есть
  **одна и та же реплика даёт разный эффект в зависимости от того, на каком этапе она произнесена**.

### 4.2. Переходы и пороги

- `STAGE_COMPLETE_THRESHOLD = 100` — прогресс подэтапа, после которого он считается пройденным.
- `Level.advanceThreshold` — минимальный `agreementProbability`, при котором пройденный контентно
  уровень (все подэтапы отработаны) действительно завершается переходом дальше; если контент
  пройден, а вероятность соглашения ещё не дозрела, игроку даётся возможность "дожать" за счёт
  оставшихся раундов, а не мгновенный переход.
- `Level.failThreshold` — если `opponent.trust` или `opponent.interest` падают до этого значения
  или ниже **в любой момент**, уровень немедленно проваливается — это проверяется первым, до всех
  остальных условий.
- `Level.maxRounds` — жёсткий лимит попыток на уровень; исчерпан без успешного перехода → провал.
- `DEAL_TIER_THRESHOLD = 85` — на последнем уровне сценария определяет, каким будет успешный исход:
  `deal` (сделка) при `agreementProbability >= 85`, иначе `partial` (частичный успех).

Все пороги калибровались по итогам живых прогонов на реальной (не mock) LLM-модели — см.
комментарии в `prisma/seed.mjs`: fallback-классификатор и настоящая модель оценивают качество
реплик по-разному (fallback заметно щедрее), поэтому числа в сиде отражают именно поведение
реальной модели, а не удобные для тестов значения.

## 5. Ветвление сценариев

Оба демо-сценария содержат развилку — прямое соответствие ТЗ, п.7.2: «хотя бы один–два полноценных
сценария с ветвлением». Ветвление реализовано не как отдельная надстройка или заранее прописанный
текстовый вариант, а как органичная часть того же детерминированного движка, работающего по тем же
правилам, что и весь остальной цикл.

### 5.1. Механизм

`Stage.branchKey` (`prisma/schema.prisma`): у обычного, неразветвлённого `Stage` он равен `null`. На
развилке **два `Stage` в рамках одного `Level` делят один и тот же `order`** и различаются
`branchKey`: `"soft"` и `"hard"`. Например, сценарий 1 («Директор по логистике») на `order=4`
второго уровня хранит две версии этапа «Возражения»:

- `branchKey: "soft"` — «Мягкие сомнения по срокам»: директор уже расположен к игроку, открытых
  возражений почти нет, нужно снять тревогу по срокам конкретным планом, не передавливая.
- `branchKey: "hard"` — «Жёсткие возражения по цене и рискам»: директор настроен скептически,
  давит на цену и риски — нужны аргументы, а не уступки.

Движок (`lib/engine/apply.ts`) копит на каждом ходу `branchSignal: { soft, hard }` — счётчик реплик
типа `RAPPORT`/`CONCESSION` (мягкая стратегия) и `PRESSURE`/`ARGUMENT` (жёсткая), начиная с начала
текущего уровня. В момент, когда прогресс подэтапа перед развилкой достигает 100 и движок должен
перейти на `order` со сразу двумя вариантами `Stage`, `lib/engine/transition.ts` **один раз**
решает: `hard`, если жёстких действий накопилось строго больше, чем мягких, иначе `soft` (ничья и
отсутствие сигнала — в пользу нейтрального `soft`, чтобы короткий путь до развилки не наказывал
игрока). Выбор фиксируется в `NegotiationState.branch` на весь оставшийся уровень — сюжет не
"прыгает" между вариантами от хода к ходу, и не решается заново на каждом последующем ходе внутри
уже выбранной ветки.

Всё остальное — поиск текущего/следующего `Stage` по `order`, подстановка контекста в LLM-промпт
реплики оппонента, запись `stageType` на `Turn`, отображение в Play UI и в разборе итогов — работает
через один и тот же branch-aware хелпер `findStageByOrder` (`lib/engine/util.ts`), так что ветвление
не потребовало отдельной ветки логики где-либо ещё в приложении.

### 5.2. Где это видно игроку и в разборе итогов

- Во время диалога реплика и тон оппонента на форк-этапе реально разные — игрок читает другой
  `title`/`description`, попавшие в промпт LLM, и это не косметика: он должен на самом деле
  преодолеть другое сопротивление в зависимости от того, как вёл разговор раньше.
- В разборе итогов раздел «По уровням» показывает, какая линия была выбрана на каждом уровне
  («линия: мягкая» / «линия: жёсткая»), так что связь между стратегией и итоговым содержанием
  разговора видна и постфактум, а не только во время игры.

### 5.3. Границы реализации

- Развилка сделана как один узел ветвления на уровень (совпадающий `order`), а не произвольное
  дерево с несколькими последовательными развилками — этого достаточно для требования ТЗ
  («хотя бы один-два сценария с ветвлением») и не усложняет модель данных сверх необходимого; при
  этом механизм (`branchKey` на `Stage`) сам по себе не ограничивает число развилок на уровень —
  расширение до цепочки развилок не потребует смены модели данных.
- Оба ответвления в текущих сценариях сходятся обратно после форк-этапа (общий следующий уровень) —
  различается контент одного этапа, а не длина всего пути. Механизм это не требует: ветки с разным
  числом последующих этапов тоже поддерживаются (движок ищет "последний" `Stage` по максимальному
  `order` среди ВСЕХ вариантов уровня, а не по фиксированной длине), но в сиде выбран более простой,
  предсказуемый для тестирования на хакатоне вариант.
- Генератор сценариев по контексту (раздел 6) сейчас создаёт линейный черновик — ветвление в
  сгенерированный сценарий администратор добавляет вручную в редакторе (создать второй `Stage` с тем
  же `order` и `branchKey` через API/будущую форму). Это осознанное разделение ответственности:
  наполнение текстом — LLM, структурные решения о ветвлении — человек.
- Админка не даёт **создать** новую развилку через форму (только редактировать текст уже
  существующих вариантов и видит их как промаркированную пару, а не как визуальный баг) — кнопки
  "вверх"/"вниз" для стадий развилки в редакторе намеренно заблокированы, чтобы админ не мог случайно
  переставить их порядок и рассинхронизировать пару.

## 6. Конфигурируемость под контекст

Администратор в `/admin` задаёт: **сферу/тему переговоров, сложность (EASY/MEDIUM/HARD), роль, тон и
цели оппонента**. По кнопке «Сгенерировать» это уходит в `POST /api/scenarios/generate` →
`generateScenarioDraft` (LLM пишет название, роль игрока, ситуацию, критерий успеха и содержимое 2
уровней с подэтапами) → создаётся **неопубликованный** черновик сценария, который администратор
проверяет и правит в обычном редакторе перед публикацией.

Числовой баланс уровня (`maxRounds`, `advanceThreshold`, `failThreshold`) считает **не LLM, а сам
эндпоинт** — по количеству подэтапов, детерминированной формулой, откалиброванной по живым прогонам
на реальной (не mock) модели в этом же проекте (раздел 4.2). Так LLM не может создать заведомо
непроходимый или наоборот тривиальный уровень числами — она отвечает только за содержание.

При `MOCK_LLM=true` или сбое сети та же кнопка создаёт валидный играбельный черновик офлайн, по
простому детерминированному шаблону на основе тех же 5 введённых параметров.

## 7. Технологии, библиотеки, внешние сервисы

- **Next.js 16 (App Router, Turbopack) + React 19 + TypeScript** — фронтенд и API-роуты в одном
  проекте.
- **Prisma 6 + PostgreSQL** — хранение сценариев/сессий; демо не «ломается» после перезапуска.
- **Tailwind CSS v4** — вся анимация (появление карточек, дыхание/кольца аватара) — чистый CSS, без
  сторонних анимационных библиотек.
- **Vitest** — автотесты (движок, LLM-клиент с моками, API-роуты).
- **Groq API** (`GROQ_API_KEY`, опционально) — LLM-вызовы (`classifyAction`, `generateOpponentReply`,
  `generateFeedback`, `generateScenarioDraft`), модель по умолчанию `openai/gpt-oss-120b`
  (настраивается через `LLM_MODEL`). Ключ получается на [console.groq.com](https://console.groq.com).
  **Не обязателен** — `MOCK_LLM="true"` полностью отключает сетевые вызовы.
- **Remotion** (`avatar-video/`, отдельный под-проект вне основного приложения) — офлайн-рендер
  Ken Burns-видео аватара оппонента из фото, сгенерированных пользователем; результат
  (`public/avatar/*.mp4`) уже лежит в репозитории, для запуска приложения Remotion не нужен.
- **GitHub Actions** — CI-пайплайн (раздел 8), без внешних сервисов и секретов.

Все переменные окружения и их назначение — в [`.env.example`](./.env.example).

## 8. Тестирование и CI

**Локально:** `npm run test` (Vitest) — юнит-тесты движка (`lib/engine/*.test.ts`: применение
действия, переходы состояний включая развилки, подсчёт счёта, настроение, факты для фидбэка),
тесты LLM-клиента (`lib/llm/client.test.ts` — классификация, генерация реплик/фидбэка/черновика
сценария, все ветки: успех / сбой сети / некорректный ответ модели / `MOCK_LLM`, без единого
реального сетевого вызова) и интеграционные тесты API-роутов (`app/api/**/*.test.ts` — с БД,
замоканной через `vi.mock("@/lib/db")`, так что тесты не требуют поднятой Postgres). Дополнительно
`npx tsc --noEmit` (типы) и `npm run lint` (ESLint).

**В CI** (`.github/workflows/ci.yml`) — четыре независимые джобы на каждый push в любую ветку и на
каждый PR в `main`: типы, линтер, тесты, прод-сборка (`next build`). Джобы независимы и идут
параллельно, так что PR получает раздельные статусы по каждой проверке, а не один общий. Сборка не
требует поднятой базы данных: единственная статически рендерящаяся при сборке страница (`/`) —
клиентский компонент, читающий данные через `fetch` в браузере, а не на сервере во время `next
build`; все остальные маршруты, обращающиеся к БД, помечены Next.js как `ƒ Dynamic` и рендерятся
по запросу.

## 9. Сборка, запуск и демонстрация

Полная инструкция локального запуска — в [`README.md`](./README.md#быстрый-старт-локальный-запуск).
Коротко: `npm install` (сам вызовет `prisma generate` через `postinstall`) → Postgres (Docker-compose
или свой) → `.env` из `.env.example` → `npx prisma migrate deploy && npx prisma db seed` → `npm run
dev`.

**Путь для демонстрации жюри:**

1. `/` — выбрать любой из двух опубликованных сценариев.
2. `/scenario/[id]` — посмотреть брифинг, нажать «Начать переговоры».
3. `/play/[sessionId]` — провести несколько реплик. Чтобы наглядно показать ветвление (раздел 5),
   пройдите один и тот же уровень дважды: один раз явно мягко (комплименты, готовность к уступкам),
   другой раз явно жёстко (давление, настойчивые аргументы без уступок) — на этапе возражений
   должен показаться разный текст оппонента, а в итогах — разная «линия» уровня.
4. Довести уровень до провала или до конца раундов — откроется экран итогов с полным разбором.
5. `/admin` — показать генерацию нового сценария по контексту (5 полей → готовый черновик) и ручной
   редактор для его донастройки, включая то, как в нём выглядит развилка.

Быстрая проверка тестами: `npm run test`. Проверка сборки как в CI: `npx tsc --noEmit && npm run
lint && npm run test && npm run build`.

## 10. Известные ограничения и возможное развитие

- **Генератор сценариев создаёт линейные черновики.** Ветвление — осознанно ручной шаг
  администратора после генерации (раздел 5.3), а не автоматика LLM: разделение ответственности
  между «LLM пишет контент» и «человек проектирует структуру» здесь настолько же принципиально, как
  и разделение Engine/LLM в основном игровом цикле (раздел 3.3). Естественное развитие — научить
  `generateScenarioDraft` предлагать и вариант развилки, оставив числовой баланс за эндпоинтом, как
  сейчас.
- **Голос/видео-ввод не реализован** (только текст) — по ТЗ не обязателен; естественное развитие —
  распознавание речи на входе с тем же пайплайном классификации после транскрипции.
- **Аватар оппонента иллюстративный** — сгенерированные пользователем фото + Ken Burns-анимация
  видео, отрендеренная офлайн через Remotion, а не «живой» ИИ-видеоаватар в реальном времени.
  Осознанный выбор, чтобы демонстрация не зависела от платного видео-API без запасного режима (ТЗ,
  раздел «чего избегать»).
- **Публичный деплой не поднят** — судьи запускают решение локально по инструкции в README (это
  прямо разрешённая ТЗ альтернатива публичной ссылке, глава 3.2 ТЗ, «Запуск для жюри»).
- **Развилка — один узел на уровень**, а не цепочка из нескольких последовательных развилок
  (раздел 5.3) — механизм это не ограничивает, выбор сделан ради предсказуемости для тестирования и
  демонстрации в рамках хакатона.
